# 设计文档（中文）

## 1. 设计目标
- 提供清晰、可用的线路规划交互：选起点/终点 → 一键规划 → 地图与列表同步展示
- 算法与数据解耦：支持从 `edges.csv` 明确定义道路/连接关系，也支持按经纬度自动生成边作为兜底
- 可部署、可复现：`docker compose up -d --build` 一键运行

## 2. API 设计

### 2.1 健康检查
- `GET /api/health`
- 返回：`{ status: "ok", time: "..." }`

### 2.2 节点列表
- `GET /api/nodes`
- 返回：节点数组 `[{ id, name, lat, lng, type?, desc?, region?, openHours?, stayMinutes? }, ...]`
- `lat/lng` 可为 `null`：坐标缺失的景点仅用于展示与维护，不参与路径计算

### 2.3 最短路径
- `GET /api/path?from=<id>&to=<id>`
- 成功返回：
  - `startId` / `endId`
  - `totalDistanceMeters`
  - `pathNodeIds` / `pathNodes`
  - `segmentDistanceMeters`
- 失败返回：`{ error: "...中文错误信息..." }`（起终点不存在或坐标缺失返回 400）

### 2.4 景点节点维护（后台）
- `GET /api/admin/nodes`：全部节点（含坐标缺失节点）
- `POST /api/admin/nodes`：新增景点；Body 为 JSON，`name` 必填，`lat/lng` 需成对提供（可同时留空），`region/openHours/stayMinutes/type/desc` 可选；未提供 `id` 时由服务端生成
- `PUT /api/admin/nodes/{id}`：按 ID 整体更新可变字段
- `DELETE /api/admin/nodes/{id}`：删除景点
- 写操作成功后自动重建路径图；校验失败返回 400 中文错误，重复 ID 返回 409，不存在返回 404

## 3. 前端交互设计

### 3.1 控制面板
- 起点/终点下拉选择（支持搜索）；坐标缺失的景点禁用并标注“缺坐标”
- 交换起终点、清空选择
- 一键规划并展示总距离与路径节点列表（含开放时间、建议停留时长）
- 右上角入口跳转景点维护后台（`/admin`）

### 3.2 地图交互
- 渲染所有坐标齐全的景点 Marker（坐标缺失的景点不上图）
- Marker Popup 支持“一键设为起点/终点”，并展示区域、开放时间、建议停留时长
- 规划成功后绘制路线 Polyline

### 3.3 景点维护后台
- 表格展示全部景点：名称、所属区域、坐标、开放时间、推荐停留、是否可参与路径计算
- 新增/编辑弹窗表单：名称必填，经纬度成对校验，停留时长非负
- 删除需二次确认；写操作成功后自动刷新节点列表

## 4. 数据与容错设计

### 4.1 CSV 数据
- `nodes.csv`：必须存在且包含列 `id,name,lat,lng`（`lat/lng` 单元格可留空表示坐标缺失）；可选列 `type,desc,region,open_hours,stay_minutes`
- `edges.csv`：可选；至少包含 `from,to`；权重列支持：`distance_meters` / `weight_meters` / `distanceMeters` / `weightMeters`

### 4.2 容错策略
- 后端：`DataLoader` 对缺列/坏行进行跳过或给出明确的中文异常提示；坐标非法按缺失处理并记录告警
- 后端：`NodeValidator` 统一校验管理接口入参（名称必填、经纬度成对、范围与长度约束）
- 后端：`GraphService` 构图时仅纳入坐标齐全的节点，坐标缺失节点不参与路径计算
- 前端：对节点 API 返回进行结构校验与清洗，避免脏数据触发运行时崩溃
- UI：ErrorBoundary 捕获不可预期异常并提示刷新重试

## 5. 性能与扩展
- 节点数量较小（景点级别）时，Dijkstra 在内存中运行即可满足交互性能
- 未来扩展点：
  - 引入真实道路网（大量边）时，可考虑启发式算法（A*）或预计算缓存
  - 为边增加更多权重维度（拥堵、票价、偏好等）
